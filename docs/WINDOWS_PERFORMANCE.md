# Оптимизации Windows в 2.1.12

- Cleanup объединяет шесть PowerShell-процессов в один. Сохраняются фильтр
  точного executable path, alias CSQTT и признаки managed NRPT.
- Четыре split route создаются одним PowerShell-процессом по порядку IPv4/IPv6,
  с `ErrorAction Stop` и проверкой наличия каждого маршрута. Ошибка вызывает откат.
- Ожидание адаптера сразу возвращает ifIndex; отдельный запрос индекса удалён.
- На обычном пути без повторных polls получается около 6 PowerShell-запусков
  вместо 15. Это подсчёт вызовов по исходникам, не измеренное ускорение в секундах.
- Статистика больше не запускает PowerShell каждые 1,5 секунды. Atomic counters
  считают IP-байты, успешно переданные между TUN и UDP bridge; dropped packets
  и внешние protocol headers не учитываются. Новый bridge начинает с нуля.
- Setup-команды следуют cancellation/timeout Connect; выход core также отменяет
  setup. Cleanup имеет независимый ограниченный timeout для восстановления сети.
- DNS-кэш ограничен 1024 записями, не сохраняет TTL=0 и возвращает оставшийся TTL.
  Запросы с EDNS/DNSSEC опциями не берутся из общего кэша. TCP fallback сохраняется.
- `[STARTUP]` в журнале показывает cleanup, первый CONFIG и routing-ready.
  Последний milestone не является доказательством первого успешного VPN-пакета.

Тесты проверяют scope/quoting batch scripts, строгие route checks, отмену
subprocess, лимит/TTL DNS-кэша, concurrent counters и identity bundled core.
Реальный выигрыш измеряется на одинаковых Windows, сервере, VK links и workers:
не менее 20 cold/warm подключений, p50/p95 и первый tunneled DNS/HTTPS отдельно.
Pacing/retry Rust, Wintun ownership и обфускация в этой версии не менялись.

## Проверка нативных API 2026-09-12 — эксперимент, не релиз

Исходный Manager: 20 последовательных подключений, 27 workers, прежние
настройки и bundled core 2.1.11. Все 20 проверок DNS, HTTPS и cleanup успешны.
Медиана / p95 от начала Connect:

| Проверка | Медиана, с | p95, с |
|---|---:|---:|
| Routing-ready | 7,297 | 7,609 |
| Успешный DNS через DNS-прокси на TUN | 7,543 | 7,828 |
| HTTPS с исходным адресом TUN | 8,209 | 8,505 |
| Disconnect + проверка очистки | 6,620 | 6,937 |

Чистый интервал CONFIG → routing-ready: медиана 5,516 с, p95 5,852 с.
Это повторные подключения без перезагрузки Windows, не 20 холодных загрузок ОС.
DNS/HTTPS запускаются последовательно после routing-ready: времена не являются
абсолютно первым пакетом, который мог пройти раньше. Cleanup включает штатную
проверку updater, поэтому не равен одной только длительности Disconnect.

Первый эксперимент перевёл IP, DNS, split и bypass routes на winipcfg. Routing-ready
сократился примерно до 3 с, но из 7 циклов ни один не прошёл одновременно DNS и HTTPS.
Появлялось подтверждение брандмауэра для нового benchmark EXE; после настройки
правил и явного выбора назначенного TUN IP ещё 3 цикла также имели сетевые ошибки.
Это отрицательный результат: такой вариант не принят и не установлен как GUI.
Причина потерь не локализована. Эти наблюдения не доказывают регрессию
нативных API: вмешательство firewall, антивируса и внешние сбои не исключены.

Уточнение по подтверждениям: монитор искал окна с названиями Windows Security,
«Безопасность Windows», Firewall/«Брандмауэр». Произвольные диалоги стороннего
антивируса он не покрывал. В раннем отчёте firewall есть пути 360 Total Security,
но это не доказывает работу его защиты в момент теста. Журнал блокировок
антивируса за время замеров не собран. Отсутствие событий нашего монитора
не является доказательством отсутствия запросов или блокировок антивируса.

В экспериментальном варианте оставлены только нативные чтение шлюза/DNS,
поиск ifIndex и добавление/удаление bypass routes. Назначение IP/метрики/DNS,
split routes, NRPT и stale cleanup остаются прежними. Попытка полного подключения
этого варианта остановилась ДО применения API — не пришёл TUNCONF за 90 с.
После восстановления штатного подключения ограниченный вариант успешно прошёл
3 контрольных цикла и ещё 1 цикл основной серии. Следующий цикл снова остановился
до CONFIG по тайм-ауту. Итого 4 успешных подключения ограниченного варианта;
20 сравнимых успешных циклов не получены. Медиана routing-ready успешных попыток
составила 7.341 с, HTTPS — 9.441 с; выборка мала и снята позже исходной серии.
Полная VPN-приёмка и устойчивый выигрыш времени Connect не подтверждены.

Отдельно выполнены 20 пар операций на Windows с проверкой одинаковых результатов:

| Операция | Старый путь, медиана | Нативный путь, медиана |
|---|---:|---:|
| Чтение шлюза | 344,4 мс | ниже разрешения измерения |
| Чтение DNS | 283,3 мс | 3,6 мс |
| Добавление + удаление маршрута | 29,5 мс | ниже разрешения измерения |

Нули в сырых измерениях коротких API-вызовов означают предел разрешения часов,
а не нулевую стоимость. В замер legacy DNS включена дополнительная сверка
с нативным результатом (около 3,6 мс), поэтому это не чистое время одной команды.
Проверены native create/readback/delete и отсутствие
присвоения владения уже существующим маршрутом. Использован временный TEST-NET-1
маршрут, не default route. Go tests/race/vet, Windows vet и Windows core tests прошли.

Данные: [evidence/windows-native-20260912](evidence/windows-native-20260912/summary.json).
В них нет паролей, VK join links или содержимого credentials.

Воспроизведение: `tools/windows-network-bench` собирается с GOOS=windows и запускается
повышенно рядом с wintun.dll и bin/csqtt-client.exe при закрытом GUI. Он читает
существующие настройки локально, не печатает их, останавливается при первой
неудачной проверке. `-cancel-ms` предназначен для отдельных fault-checks, не
для сравнения производительности. Нативный парный тест требует явных
`CSQTT_NATIVE_LIVE_TEST=1` и `CSQTT_NATIVE_REPORT=<путь>`.

Следующий допуск: собрать события антивируса/firewall и установить, какие EXE
были разрешены во время каждого цикла; восстановить стабильное получение TUNCONF, затем провести
сравнимую VPN-серию ограниченного варианта и проверку отмены/аварии. До этого
не выпускать нативные изменения и не заменять рабочий GUI этим экспериментом.

По завершении временные TEST-NET маршруты отсутствовали. Рабочий GUI EXE не
заменялся экспериментальной сборкой; сохранено подключение штатного клиента.
На тестовом ПК заранее добавлены правила для конкретных CSQTT/benchmark EXE;
первоначальные разрешения, принятые пользователем, восстановлены для одинаковых
условий сравнения. Глобальный firewall/UAC не отключались. Это настройка стенда,
не реализованный installer-flow для всех пользователей. Монитор подтверждений
после настройки не зарегистрировал новых окон; после тестов остановлен.
